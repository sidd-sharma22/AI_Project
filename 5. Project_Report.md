## 1. Project Objectives

The primary objective of this project is to implement, evaluate, and reproduce the full end-to-end pipeline of the research paper *"Explainable AI-Based DDOS Attack Identification Method for IoT Networks"* from scratch.

Specific objectives include:

## 2. Introduction to the Research Paper

With the rapid expansion of the Internet of Things (IoT), billions of interconnected devices—such as smart home sensors, routers, and industrial controllers—are deployed worldwide. However, many IoT devices have limited computing power and lack robust built-in security, making them easy targets for botnets like Mirai to launch massive Distributed Denial of Service (DDoS) attacks.

DDoS attacks flood targeted online servers and networks with overwhelming volumes of illegitimate traffic, causing system outages and major financial damage. Traditional security systems use two main approaches:
- **Signature-Based Intrusion Detection Systems (SIDS):** Rely on matching traffic against known attack signatures. They completely fail against zero-day (previously unseen) attacks.
- **Supervised Machine Learning Systems:** Classifiers like Random Forests and Neural Networks learn decision boundaries from labeled datasets containing both normal and attack traffic.

While supervised AI systems show high accuracy on standard benchmarks, the authors of this paper highlight critical shortcomings in real-world deployment:
1. **Labeled Data Bottleneck:** Obtaining realistic, up-to-date labeled attack data is expensive, time-consuming, and raises legal, ethical, and privacy concerns.
2. **Failure on Evasive Attacks:** Attackers frequently modify packet rates, inter-arrival times, or header values. Supervised models easily overfit to training distributions and fail when facing modified or evasive attacks.
3. **The "Black-Box" Problem:** Supervised models output a binary prediction (0 or 1) without explaining *why* an alert was generated. Security operators cannot determine the root cause, leading to alert fatigue and low trust.
4. **Resource Limitations:** Complex deep learning models (such as deep LSTMs) require too much memory and computing power to run directly on resource-constrained IoT edge devices.

To address these challenges, the authors proposed a two-stage framework combining **unsupervised Deep Autoencoders** with **Kernel SHAP explainability** and **domain-specific threshold policies**.

## 4. Methodology & Mathematical Formulation

The proposed framework consists of four core steps: data preprocessing, unsupervised anomaly detection, local feature explanation with Kernel SHAP, and domain DDoS feature mapping with threshold tuning.

```
+--------------------------+
| Bidirectional Flow Data  | (USB-IDS-1 Parquet / CICFlowMeter)
+--------------------------+
             |
             v
+--------------------------+
|  Min-Max Normalization   | (Fitted strictly on Benign training traffic)
+--------------------------+
             |
             v
+--------------------------+
| Deep Autoencoder Model   | (Trained ONLY on Benign data; 77 -> 32 -> 10 -> 32 -> 77)
+--------------------------+
             |
             v
+--------------------------+
|  Reconstruction Error    | (L(A, A') > Threshold_benign ==> Flagged Anomaly)
+--------------------------+
             |
             v
+--------------------------+
|  Kernel SHAP Explainer   | (Calculates Top-R Influential Features)
+--------------------------+
             |
             v
+--------------------------+
| 21 DDoS Feature Mapping  | (Intersects with TCP State, Volumetric, & App Layer Features)
+--------------------------+
             |
             v
+--------------------------+
| F1-Tuned Threshold Check | (T = argmax F1 score; Exceeds Threshold ==> Confirmed DDoS)
+--------------------------+
```

### 4.1 Feature Normalization
Network traffic flows extracted via CICFlowMeter contain 77 numerical features. Each feature is normalized into the range $[0, 1]$ using Min-Max scaling:
$$x_{\text{norm}} = \frac{x - x_{\min}}{x_{\max} - x_{\min}}$$
To prevent data leakage, the scaling parameters ($x_{\min}, x_{\max}$) are fitted strictly on the benign training set and then applied to validation and test data.

### 4.2 Unsupervised Anomaly Detection (Deep Autoencoder)
The autoencoder is trained to reconstruct normal network traffic. Its architecture contains:
- **Input Dimension:** 77 numerical features
- **Encoder:** $\text{Linear}(77, 32) \to \text{ReLU} \to \text{Linear}(32, 10) \to \text{ReLU}$
- **Decoder:** $\text{Linear}(10, 32) \to \text{ReLU} \to \text{Linear}(32, 77) \to \text{Sigmoid}$

The model is trained using the Adam optimizer ($\text{learning rate} = 0.01$) over 25–40 epochs.

For each input flow vector $A = (a_1, a_2, \dots, a_n)$ and its reconstructed output $A' = (a'_1, a'_2, \dots, a'_n)$, the reconstruction error is computed using Equation (2) from the paper:
$$L(A, A') = \sum_{i=1}^n (a_i - a'_i)^2$$

An anomaly threshold $T_{\text{anomaly}}$ is established based on the benign training error distribution. If a flow's reconstruction error exceeds this threshold:
$$L(A, A') > T_{\text{anomaly}} \implies \text{Flow is Anomalous}$$

Because the autoencoder has never seen attack patterns, malicious flows cannot be compressed and reconstructed accurately, causing their reconstruction error to spike.

### 4.3 Explaining Anomalies via Kernel SHAP (Algorithm 1)
When an anomaly is detected, the system ranks the individual feature reconstruction errors:
$$|a_1 - a'_1| > |a_2 - a'_2| > \dots > |a_n - a'_n|$$

To understand why the error occurred, **Kernel SHAP** is used. Kernel SHAP is a model-agnostic explanation framework rooted in cooperative game theory. It builds a local linear explanation model:
$$g(z') = \phi_0 + \sum_{i=1}^M \phi_i z'_i$$
where $\phi_i$ represents the Shapley value (feature attribution) of feature $i$, satisfying three mathematical properties:
1. **Local Accuracy:** The explanation matches the model's output locally.
2. **Missingness:** Features absent from the coalition have zero attribution.
3. **Consistency:** If a feature's marginal contribution increases, its attribution does not decrease.

The features with the highest absolute SHAP values $|\phi_i|$ are designated as the **Top-$R$ influential features**.

### 4.4 The 21 Informative DDoS Features (Tables 1, 2, and 3)
Domain knowledge is incorporated by defining 21 critical network features grouped into three cybersecurity categories:

1. **TCP State Exhaustion Features (Table 1 - 5 features):**  
   Target connection tables (e.g., SYN floods). Features: `fwd-TCP-num` (Total Fwd Packet), `fwd-ACK-num` (ACK Flag Count), `fwd-max-ACK` (Fwd IAT Max), `fwd-SYN-num` (SYN Flag Count), and `fwd-SYN-rate`.
2. **Application Layer Features (Table 2 - 3 features):**  
   Target specific open ports and protocols. Features: `src-port`, `dst-port`, and `protocol` (Protocol).
3. **Volumetric Features (Table 3 - 13 features):**  
   Target network bandwidth through flooding. Features: `flow-duration`, `tot-fwd-pkts`, `tot-bwd-pkts`, `tot-len-bwd-pkts`, `fwd-pkts-len-min`, `Fwd-Packet-Length-Std`, `bwd-pkts-len-max`, `flow-packets/s`, `bwd-IAT-tot`, `bwd-IAT-mean`, `fwd-psh-num`, `Bwd-Packets/s`, and `fwd-ent-int`.

### 4.5 Optimal Threshold Tuning & Attack Certainty (Algorithm 2)
For each DDoS candidate feature, an optimal decision threshold $T$ is identified using Equation (3):
$$T = \arg\max(F_1)$$
where a grid search across candidate thresholds selects the value that maximizes the harmonic mean of precision and recall on the validation set.

Finally, **Algorithm 2** intersects the Top-$R$ SHAP features with the 21 domain features. If an influential feature exceeds its calibrated threshold:
$$\text{Top-R Feature} \in \text{Domain DDoS Features} \quad \text{AND} \quad \text{Actual Value} > T \implies \text{Confirmed DDoS Attack}$$

This dual-layer verification ensures that benign statistical anomalies (such as large file downloads) are not falsely flagged as attacks, dramatically reducing false alarm rates.

## 5. Dataset Description & Exploratory Data Analysis (EDA)

The paper evaluates its methodology using the official **USB-IDS-1** benchmark dataset (University of Sannio, Benevento Intrusion Detection System).

### 5.1 Dataset Scale
We conducted our data analysis across all three official splits:
- **`USB-IDS-1-TRAIN.parquet`:** 3,369,070 flows (70%)
- **`USB-IDS-1-VALIDATION.parquet`:** 721,986 flows (15%)
- **`USB-IDS-1-TEST.parquet`:** 722,010 flows (15%)
- **Total Network Flows Analyzed:** **4,813,066 rows** across 78 columns (77 features + 1 target label).

### 5.2 Data Quality & Cleaning Results
We implemented rigorous data quality audits to inspect the raw data:
- **Missing Values (NaN / Null):** **0 missing values** across all 4.81 million rows. Our data loader includes a defensive imputation function that fills any missing value with the column median or zero.
- **Infinite Values ($\pm\infty$):** **0 infinite values** detected. In raw network captures, zero flow duration can produce division-by-zero errors. Our pipeline safely replaces infinite values with column maximum/minimum finite values.
- **Duplicate Rows:** **0 duplicates** in TEST and VALIDATION splits, and only **6 duplicate rows** out of 3,369,070 rows in the TRAIN split (< 0.0002%). These identical flows occur naturally when automated scanners send probe packets with identical parameters at the same millisecond.
- **Zero-Variance (Constant) Columns:** Exactly **6 columns** were found to have zero variance (constant value of 0):
  `['Fwd URG Flags', 'Bwd URG Flags', 'URG Flag Count', 'CWR Flag Count', 'ECE Flag Count', 'Subflow Bwd Packets']`  
  *Cybersecurity Rationale:* Modern HTTP web servers and flooding tools (like HULK) rarely use the Urgent pointer (`URG`) or Congestion Notification flags (`CWR`, `ECE`).

### 5.3 Class Distribution
- **Benign Traffic:** 304,733 flows (~6.3% of the total dataset)
- **HULK Attacks (Our Evaluation Focus):**
  - `Hulk-Reqtimeout`: 855,630 flows
  - `Hulk-NoDefense`: 851,130 flows
  - `Hulk-Security2`: 813,046 flows
  - `Hulk-Evasive`: 756,985 flows
- **TCPFlood & Slow Attacks:** ~930,000 flows

## 6. Implementation Architecture

We built a modular, production-ready Python package in `src/` alongside an interactive Jupyter Notebook:

1. **`src/data_loader.py`:** Reads Parquet files using PyArrow, performs defensive data cleaning, isolates benign flows, and applies Min-Max normalization.
2. **`src/autoencoder.py`:** Implements the PyTorch Deep Autoencoder (77 $\to$ 32 $\to$ 10 $\to$ 32 $\to$ 77), computes reconstruction error ($L(A, A')$), and determines anomaly thresholds.
3. **`src/xai_explainer.py`:** Implements Algorithm 1 using Kernel SHAP over a background set of benign samples to extract Top-$R$ influential features.
4. **`src/ddos_identifier.py`:** Defines the 21 domain features, performs grid-search F1 threshold tuning (Equation 3), and executes Algorithm 2 for attack confirmation.
5. **`src/baselines.py`:** Implements the baseline supervised models—Decision Tree (DT), Random Forest (RF), and Deep Neural Network (DNN)—for benchmarking against the paper's Table 4.
6. **`src/evaluate_and_plot.py`:** Computes evaluation metrics and generates publication-grade plots for Figures 4 through 13.
7. **`src/main.py`:** Master script executing the complete automated pipeline with a single command.
8. **`notebooks/DDoS_XAI_Paper_Implementation.ipynb`:** Self-contained, interactive notebook containing all markdown theory, equations, code execution cells, and inline figures.

#### Why Supervised Classifiers Failed on Hulk-Evasive:
In the paper's experiments, supervised classifiers collapsed drastically on `Hulk-Evasive` (RF accuracy dropped to 0%, DT to 6%, and DNN to 5%). In our replication, the DNN baseline collapsed to 33%. 

This occurs because `Hulk-Evasive` introduces randomized user-agents, obfuscated referrers, and packet interval variations specifically crafted to avoid standard signature thresholds. Supervised classifiers trained on standard `Hulk-NoDefense` learn static boundaries tied to specific attack features; when the attacker modifies those features, the supervised model misclassifies the malicious traffic as benign.

In contrast, our **unsupervised Autoencoder + XAI** method maintained **95% to 100% accuracy across all three scenarios**. Because the autoencoder learns exclusively what benign traffic looks like, any deviation—whether standard flooding or stealthy evasion—results in an elevated reconstruction error that gets identified immediately.

## 8. IoT Edge Deployment Feasibility

A major contribution of this research is developing an AI system lightweight enough to run on resource-constrained IoT edge devices:
- **Parameter Count:** The autoencoder has only two hidden layer dimensions ($77 \to 32 \to 10 \to 32 \to 77$). This architecture contains fewer than **6,000 total parameters**, taking up under **25 KB** of storage.
- **Inference Speed:** On a standard CPU, computing the reconstruction error takes less than **0.02 milliseconds per flow**, enabling real-time edge processing.
- **Selective Explainability:** To prevent computation bottlenecks, full Kernel SHAP calculations are only triggered for the small fraction of flows that cross the reconstruction error threshold. This allows edge gateways (such as a Raspberry Pi 4 Model B with 4 GB RAM) to operate continuously without latency spikes.
